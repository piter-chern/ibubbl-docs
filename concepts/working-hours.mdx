---
title: 'Working Hours & Scheduling'
description: 'How iBubbl respects working hours for outbound sends.'
---

iBubbl never sends an iMessage outside of the recipient's working hours. This protects your sender reputation and respects contact preferences — late-night blasts are the fastest way to get a phone number flagged.

## How it works

Every outbound message — sent from the dashboard, `POST /v1/messages`, a workflow, a scheduled send or an integration — waits for the recipient's working hours before it leaves your device:

- `POST /v1/messages` accepts the send straight away (`202 Accepted`) with `status: "pending"`, whatever the time.
- If the **recipient's local time** is inside your working window, the message goes out within seconds.
- If it is outside, the message stays `pending` and goes out automatically when the window next opens. There is no separate status or webhook for this wait; a [`message.sent`](/webhooks/events) webhook fires when it goes out.

You don't need to do anything to opt in. The behavior is on by default for every account.

## Configuring working hours

Working hours are set in the dashboard at **Settings → Sending Hours**. Defaults for new accounts:

| Day | Sends allowed |
| --- | ------------- |
| Monday – Saturday | 09:00 – 20:00 |
| Sunday | 12:00 – 20:00 |

The end time is exclusive: with the default window, sends pause at 8:00 PM. The window is applied in each **contact's** timezone (see below), so there is no timezone setting on the window itself.

These are only your **sending** hours. When people can book meetings with you is a separate setting, **Settings → Booking Hours**, in your own time zone.

You can configure different windows per day of the week, or close specific days entirely. The dashboard is the only way to manage these settings — there's no API surface for them today.

## Per-contact timezone

The local time check uses the **contact's timezone**, not your account's. iBubbl determines a contact's timezone in this order:

1. **Explicit override** — if you set the `timezone` field on the contact (via [`POST /v1/contacts`](/api-reference/contacts/upsert) or the dashboard).
2. **Area-code inference** — for North American numbers, iBubbl infers a default timezone from the area code (e.g., `+1415...` → `America/Los_Angeles`).
3. **Account timezone** — the timezone in your dashboard's **Settings → Notifications**, which starts as your browser's timezone.
4. **`America/New_York`** — if none of the above is set.

To override the inferred timezone, pass it on contact upsert:

```bash
curl -X POST https://web-production-4e09a.up.railway.app/v1/contacts \
  -H "Authorization: Bearer $IB_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "phone": "+14155551234",
    "timezone": "America/New_York"
  }'
```

The override is sticky — once set, automation re-upserts will not overwrite it.

## Detecting a held send

A message waiting for working hours is `pending`, like one that is about to go out. [`GET /v1/messages/{id}`](/api-reference/messages/retrieve) tells them apart with two fields:

```json
{
  "id": "msg_4a5b6c7d-...",
  "status": "pending",
  "to": "+14155551234",
  "held_reason": "working_hours",
  "held_until": "2026-10-08T16:00:00+00:00"
}
```

- `held_reason` — why it is waiting right now: `working_hours`, or `busy_window` when your connected calendar shows you busy.
- `held_until` — when it is **expected** to go out: the contact's next opening, or the end of the busy block if one covers that opening. It is recomputed within about 10 seconds when your hours or calendar change, and it is `null` if no sending day is enabled.

Both are `null` when the message is not being held. A held message is first marked within about 10 seconds of being accepted, so a `GET` immediately after `POST` may not show the hold yet. A [`message.sent`](/webhooks/events) webhook fires when it goes out.

## Capacity holds (`status: "queued"`)

Separately from working hours, a send can be accepted but parked because of capacity. The response is still `202 Accepted`, with `status: "queued"`, and the reason is in the `failed_reason` field of the [`message.queued`](/webhooks/events) webhook:

- `hourly_cap_hit` — your line hit its hourly send cap.
- `line_offline` — your sending line is temporarily disconnected.

iBubbl re-checks queued messages every 30 seconds and sends them as soon as the condition clears. A message still queued after **one hour** is dropped and moves to `status: "expired"`; send it again if it still matters.

Daily and cold-outreach caps do **not** queue: a send over those caps fails immediately with a `422`. See [Errors](/errors).
