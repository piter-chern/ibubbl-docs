With the iBubbl API, your software sends real iMessages, the blue bubbles, from a dedicated line that iBubbl runs for you, and gets every reply pushed to your server, usually within a minute. There's no phone, Apple ID or hardware to manage on your side.

- **Send messages** to one contact or to a group, from your iBubbl line. When the recipient can't be reached on iMessage, the message goes out as a text instead, and its `channel` tells you which.
- **Receive replies and status changes** as [webhooks](/webhooks/overview): inbound messages, sent / delivered / read, reactions, edits and opt-outs.
- **Keep contacts in sync**: create, update and tag them.
- **Stay compliant by default**: opt-outs, each contact's sending hours and your line's send limits are enforced for you.

The API is HTTPS and JSON, authenticated with one Bearer API key. There's no SDK to install: any HTTP client works.

```bash
# One key per message: generate it once, and reuse it if you retry.
IDEMPOTENCY_KEY=$(uuidgen)

curl -X POST https://api.ibubbl.com/v1/messages \
  -H "Authorization: Bearer $IBUBBL_API_KEY" \
  -H "Content-Type: application/json" \
  -d "{
    \"to\": \"+14155551234\",
    \"body\": \"Hey Sam, quick check-in about your order.\",
    \"idempotency_key\": \"$IDEMPOTENCY_KEY\"
  }"
```

The API answers `202 Accepted` right away; the message then goes out from your line, and its progress arrives as webhook events. The [Quickstart](/quickstart) walks through it end to end, sending to your own phone.

<Note>
Every request is live: there is no sandbox or test mode, and a send delivers a real message. You need an active iBubbl line before you can send; iBubbl sets it up for you.
</Note>

## Base URL

```
https://api.ibubbl.com
```

All endpoints are under `/v1`. See [Versioning](/versioning) for what can and can't change within it.
