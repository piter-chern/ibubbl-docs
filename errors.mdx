Every iBubbl API error response uses the same envelope shape:

```json
{
  "detail": {
    "error": "validation_error",
    "message": "Exactly one of contact_id, to, chat_guid, or participant_phones is required"
  }
}
```

The `error` field is a **stable machine-readable code** — branch your integration's logic on this, not on the HTTP status or `message`. The `message` field is human-readable and may change without notice.

## Request IDs

Every response from `api.ibubbl.com`, successful or not, carries an `X-Request-Id` header. It names that one request in iBubbl's logs. When something goes wrong, log it next to the error and quote it to [support@ibubbl.com](mailto:support@ibubbl.com): it finds your request faster than a timestamp and a request body can.

<CodeGroup>

```bash cURL
# -D - prints the response headers, including X-Request-Id.
curl -sS -D - https://api.ibubbl.com/v1/messages/8b3a4e72-1c2d-4e5f-9a0b-2c3d4e5f6a7b \
  -H "Authorization: Bearer $IBUBBL_API_KEY"
```

```typescript TypeScript
const messageId = "8b3a4e72-1c2d-4e5f-9a0b-2c3d4e5f6a7b";

const res = await fetch(`https://api.ibubbl.com/v1/messages/${messageId}`, {
  headers: { Authorization: `Bearer ${process.env.IBUBBL_API_KEY}` },
  signal: AbortSignal.timeout(10_000),
});

const data = await res.json();
if (!res.ok) {
  const requestId = res.headers.get("x-request-id");
  throw new Error(`${res.status} ${data.detail?.error} (request ${requestId})`);
}
```

```python Python
import os

import requests

API_KEY = os.environ["IBUBBL_API_KEY"]

message_id = "8b3a4e72-1c2d-4e5f-9a0b-2c3d4e5f6a7b"

res = requests.get(
    f"https://api.ibubbl.com/v1/messages/{message_id}",
    headers={"Authorization": f"Bearer {API_KEY}"},
    timeout=10,
)
data = res.json()
if not res.ok:
    request_id = res.headers.get("X-Request-Id")
    raise RuntimeError(f"{res.status_code} {data['detail']['error']} (request {request_id})")
```

</CodeGroup>

**Send your own ID to trace a request end to end.** If your request carries an `X-Request-Id` header, iBubbl uses it as the request's ID and returns it unchanged, so the same ID appears in your logs and ours. It must be 1–128 characters of letters, digits, `.`, `_`, `:` and `-`. Anything else is ignored, and iBubbl generates an ID instead. Reusing one ID for several requests is allowed, but a unique ID per request is easier to find.

## Error catalog

<ResponseField name="unauthorized" type="401">
  Missing, malformed, or revoked API key. Verify the `Authorization: Bearer ib_pk_<hex>` header and that the key is active in your dashboard.
</ResponseField>

<ResponseField name="forbidden" type="403">
  Your API key is valid, but your iBubbl account is suspended or cancelled (`message` is `Account is suspended` or `Account is cancelled`). Every API-key endpoint returns this. A resource that belongs to another account is never a 403: it returns `not_found`.
</ResponseField>

<ResponseField name="not_found" type="404">
  The requested resource doesn't exist, OR it exists but belongs to a different customer (existence is hidden across tenants). Verify the resource ID is correct and was created on the same account whose key you're using. A [deleted contact](/api-reference/contacts/delete) answers `404` too, including as the `contact_id` of a send.
</ResponseField>

<ResponseField name="line_not_found" type="404">
  [Retrieve a line](/api-reference/lines/retrieve): no line with that ID on your account. A malformed ID and another account's line are answered the same way. Line IDs come from [List lines](/api-reference/lines/list) and from `line_id` on messages and webhooks.
</ResponseField>

<ResponseField name="idempotency_conflict" type="409">
  You reused an `idempotency_key` with a request payload that doesn't match the one originally cached. Either generate a new key for this distinct send, or fix your retry logic to reuse the original payload byte-for-byte. Keys are shared by [Send a message](/api-reference/messages/send) and [Schedule a message](/api-reference/scheduled-messages/create), so a key used on one is this error on the other (`message` names the endpoint that used it). On a scheduled message the payload includes `send_at`: to move it, [update it](/api-reference/scheduled-messages/update). See [Idempotency](/idempotency).
</ResponseField>

<ResponseField name="edit_in_flight" type="409">
  [Edit a message](/api-reference/messages/edit) and [Unsend a message](/api-reference/messages/unsend): an earlier edit of the message hasn't reached the recipient yet. Wait for [`message.edited`](/webhooks/events#message-edited) (usually a few seconds), then send the request again. Nothing changed.
</ResponseField>

<ResponseField name="already_unsent" type="409">
  [Edit a message](/api-reference/messages/edit): the message was unsent (or is being unsent), so there is nothing left to edit.
</ResponseField>

<ResponseField name="scheduled_message_sending" type="409">
  [Update](/api-reference/scheduled-messages/update) and [cancel](/api-reference/scheduled-messages/cancel) a scheduled message: it is being turned into a message right now. Nothing changed. It settles within seconds as `fired` (then [`scheduled_message.fired`](/webhooks/events#scheduled-message-fired)) or `failed`; after it fires, the message itself can be [cancelled](/api-reference/messages/cancel) while it waits to go out.
</ResponseField>

<ResponseField name="scheduled_message_changed" type="409">
  [Update](/api-reference/scheduled-messages/update) a scheduled message: other requests kept changing it between this one's read and its write, so it was checked again each time and still couldn't be applied. [Send it now](/api-reference/scheduled-messages/send-now): another request moved it to a later `send_at` at the same moment. Nothing changed and nothing was sent. Read it again, then retry if the change still makes sense.
</ResponseField>

<ResponseField name="message_dispatching" type="409">
  [Cancel a message](/api-reference/messages/cancel): your line has already picked the message up to send it, so it can't be stopped. It goes out, and `message.sent` fires. Within 110 seconds of sending you can still [unsend it](/api-reference/messages/unsend).
</ResponseField>

<ResponseField name="validation_error" type="422">
  Generic request-shape failure. The `message` will identify the field. Common causes: missing required body field, malformed E.164 phone, body length zero, `to` and `contact_id` both omitted, neither `body` nor `attachments`, an `attachments` entry that is neither an `https` URL nor a file ID (or more than 10 of them), `attachments` with `chat_guid` or `participant_phones`, or `attachments` with `effect` or `reply_to_message_id`. On [Upload a file](/api-reference/files/upload): a body that isn't `multipart/form-data`, no part named `file`, another part or a second file, an empty file, or a cut-off body. On a list endpoint: an unknown or repeated query parameter, `limit` outside 1–100, or a time without a time zone. An `idempotency_key` starting with `sched:` (reserved). On [Schedule a message](/api-reference/scheduled-messages/create) and [Update a scheduled message](/api-reference/scheduled-messages/update): any field not in the body, a `send_at` without a time zone, a `null` `send_at` or `link_preview`, an update with no field, or a `link_preview` the message can't have (a body that doesn't end in exactly one link, or files, an effect or a reply), including an update that would break it.
</ResponseField>

<ResponseField name="send_at_too_soon" type="422">
  [Schedule](/api-reference/scheduled-messages/create) or [update](/api-reference/scheduled-messages/update) a scheduled message: `send_at` is in the past or less than 1 minute from now. To send now, use [Send a message](/api-reference/messages/send).
</ResponseField>

<ResponseField name="send_at_too_far" type="422">
  [Schedule](/api-reference/scheduled-messages/create) or [update](/api-reference/scheduled-messages/update) a scheduled message: `send_at` is more than 90 days from now.
</ResponseField>

<ResponseField name="scheduled_limit_reached" type="422">
  [Schedule a message](/api-reference/scheduled-messages/create): your account already has 5,000 scheduled messages waiting (dashboard ones included). Cancel some, or wait for them to fire.
</ResponseField>

<ResponseField name="scheduled_group_unsupported" type="422">
  [Schedule a message](/api-reference/scheduled-messages/create): the request names a group (`chat_guid`, `participant_phones` or `group_name`). Only one-to-one messages can be scheduled for now.
</ResponseField>

<ResponseField name="scheduled_empty" type="422">
  [Update a scheduled message](/api-reference/scheduled-messages/update): `"body": null` (or `""`) on a scheduled message without files would leave nothing to send. Send new text, or cancel it.
</ResponseField>

<ResponseField name="invalid_cursor" type="422">
  List endpoints only: `starting_after` is a UUID but not the `id` of one of your items (another account's ID, and a contact deleted since, are answered the same way). Pass the `id` of the last item from the previous page, with the same endpoint. See [Pagination](/concepts/pagination).
</ResponseField>

<ResponseField name="contact_opted_out" type="422">
  The destination contact has opted out and cannot receive new sends. iBubbl enforces this server-side; there is no programmatic way to override. [Add a tapback](/api-reference/messages/react) and [Start typing](/api-reference/conversations/start-typing) return it too, in a one-to-one conversation. See [Suppression & Opt-Outs](/concepts/suppression).
</ResponseField>

<ResponseField name="contact_blocked" type="422">
  A one-to-one send to a contact your account has blocked, in the dashboard or with [Block a contact](/api-reference/contacts/block). Nothing was sent. The send works again once the contact is [unblocked](/api-reference/contacts/unblock). If a contact is both opted out and blocked, you get `contact_opted_out`. [Add a tapback](/api-reference/messages/react) and [Start typing](/api-reference/conversations/start-typing) return it too, in a one-to-one conversation.
</ResponseField>

<ResponseField name="unresponsive_contact" type="422">
  Refused on the 7th consecutive message to a contact who has never replied: iBubbl allows 6 unanswered messages in a row, then stops. Messages still waiting to go out (`pending` or `queued`) count toward the 6. Nothing was sent. The limit lifts as soon as the contact replies; waiting does not reset it.
</ResponseField>

<ResponseField name="invalid_timezone" type="422">
  The `timezone` field on a contact upsert is not in the supported IANA allowlist. The supported set covers US/Canada timezones plus common international zones; if you need a zone that isn't supported, email [support@ibubbl.com](mailto:support@ibubbl.com).
</ResponseField>

<ResponseField name="invalid_email" type="422">
  The `email` on a contact create or update doesn't look like an email address (`name@domain.tld`, no spaces, at most 254 characters). Nothing was saved.
</ResponseField>

<ResponseField name="invalid_tag" type="422">
  A tag name is empty, longer than 64 characters, or holds an invisible character. On a contact create, nothing was saved.
</ResponseField>

<ResponseField name="duplicate_tag" type="422">
  A tag name collides with an existing tag in a way iBubbl can't resolve. Rare: choose a different name.
</ResponseField>

<ResponseField name="line_offline" type="queued">
  On [Look up a number](/api-reference/imessage-lookups/create) it is a `503`: none of your lines is online to ask Apple right now. Nothing was queued; try again in a few minutes. On a send, your line's Mac is offline. This is not returned as an error: a one-to-one send to a contact your line has messaged before is accepted (`202`, `status: "queued"`) and goes out automatically when the Mac reconnects. The reason appears only as `failed_reason` on the [`message.queued`](/webhooks/events) webhook; the message itself shows `failed_reason: null` while it's queued. If it is still queued 60–65 minutes after it was accepted it expires (`status: "expired"`), and [`message.failed`](/webhooks/events#message-failed) fires with `failed_reason: "queue_expired"`. A contact with no line yet gets `no_eligible_line` instead. See [Limits and queues](/concepts/limits#offline-lines).
</ResponseField>

<ResponseField name="daily_cap_exhausted" type="422">
  The line has sent 1,000 messages today, its daily ceiling. Every outbound message counts: new contacts, replies, follow-ups, groups, messages still waiting and failed ones. The send fails and is not queued; the count resets at midnight ET (America/New_York), so send again after that. See [Limits and queues](/concepts/limits).
</ResponseField>

<ResponseField name="cold_cap_exhausted" type="422">
  The line has messaged 50 new contacts today (contacts your account has no history with). The send fails and is not queued. Messages to contacts already counted today, and to anyone you've messaged before, still go out. The count resets at midnight ET (America/New_York). See [Limits and queues](/concepts/limits).
</ResponseField>

<ResponseField name="hourly_cap_hit" type="queued">
  Legacy: not used on any current line. The hourly limit on new contacts is a hold instead: the message stays `pending` with `held_reason: "hourly_limit"` and goes out by itself. See [Limits and queues](/concepts/limits).
</ResponseField>

<ResponseField name="followup_cap_exhausted" type="422">
  Legacy: not used on any current line. It was a daily cap on follow-ups under the older per-line caps.
</ResponseField>

<ResponseField name="no_eligible_line" type="422">
  No line on your account can take this request right now: for example, a contact you haven't messaged before while your line is offline, or a group whose line is no longer active. Nothing was sent. Send again once your line is back online. A [scheduled message](/api-reference/scheduled-messages/create) that finds no line when it fires fails with `failed_reason: "no_eligible_line"`; scheduling one to a contact you have no conversation with while no line of yours is active is `503 no_active_line` instead.

  Also returned by [Edit](/api-reference/messages/edit), [Unsend](/api-reference/messages/unsend), [Add a tapback](/api-reference/messages/react), [Remove a tapback](/api-reference/messages/remove-reaction) and [Start typing](/api-reference/conversations/start-typing) when the line the message or conversation is on is no longer active on your account, for example because it was moved to another account. Those requests won't succeed later: don't retry them.
</ResponseField>

<ResponseField name="group_not_found" type="404">
  The `chat_guid` doesn't match a group conversation on your account. A group's `chat_guid` can change when someone is added to it, so look up the current one. Retrying the same request won't help.
</ResponseField>

<ResponseField name="group_outbound_blocked_suppression" type="422">
  One or more participants in the group have opted out, so iBubbl won't send to the group. When the send would create a new group, `detail` also carries a `blocked_phones` list naming them. Opt-outs are permanent, so retrying won't help; send to a group without them.
</ResponseField>

<ResponseField name="insufficient_participants" type="422">
  The `participant_phones` resolve to fewer than 2 different people: for example, the same number written two ways. A group needs at least 2 different participants; for one person, send one-to-one.
</ResponseField>

<ResponseField name="reply_target_not_found" type="422">
  `POST /v1/messages` only: `reply_to_message_id` doesn't name a message in the conversation you're sending to. For a `to` or `contact_id` send it must be a message with that contact, one-to-one; for a `chat_guid` send, a message in that group. A message from another account is answered the same way. Check the ID and the addressing field. See [Reply and send with effects](/guides/send-messages#reply-to-a-message-and-send-with-effects).
</ResponseField>

<ResponseField name="reply_target_unsent" type="422">
  `POST /v1/messages` only: the contact unsent the message `reply_to_message_id` points to, so it can't be quoted. Send without `reply_to_message_id`.
</ResponseField>

<ResponseField name="reply_target_partly_unsent" type="422">
  `POST /v1/messages` only: the contact unsent part of the message `reply_to_message_id` points to, and your line can't quote what's left. Send without `reply_to_message_id`.
</ResponseField>

<ResponseField name="invalid_target" type="422">
  [Add a tapback](/api-reference/messages/react): the message is one you sent; tapbacks go only on messages you received. [Edit](/api-reference/messages/edit) and [Unsend](/api-reference/messages/unsend): the message is one you received; only messages you sent can be changed.
</ResponseField>

<ResponseField name="sms_not_supported" type="422">
  [Add a tapback](/api-reference/messages/react): the message came in by SMS, or the conversation's latest messages are going out by SMS, and tapbacks can't be sent over SMS. They work over iMessage and RCS. See [Tapbacks, read receipts and typing](/guides/reactions-read-receipts-typing#tapbacks). [Edit](/api-reference/messages/edit) and [Unsend](/api-reference/messages/unsend): the message went out by SMS (RCS included), where messages can't be edited or unsent; only iMessage messages can. Nothing was sent or changed.
</ResponseField>

<ResponseField name="not_sent_yet" type="422">
  [Edit](/api-reference/messages/edit) and [Unsend](/api-reference/messages/unsend): the message is still `pending` or `queued`, so there's nothing on the recipient's phone to change. [Cancel it](/api-reference/messages/cancel) and send a new one.
</ResponseField>

<ResponseField name="not_editable" type="422">
  [Edit a message](/api-reference/messages/edit): the message can't be edited. It has no text (only files), or it failed, was cancelled or expired, or iMessage never confirmed it. Send a follow-up message instead. On [Update a scheduled message](/api-reference/scheduled-messages/update): it has already fired, failed or been cancelled. On [Send a scheduled message now](/api-reference/scheduled-messages/send-now): it failed or was cancelled.
</ResponseField>

<ResponseField name="not_unsendable" type="422">
  [Unsend a message](/api-reference/messages/unsend): the message failed, was cancelled or expired, or iMessage never confirmed it, so there's nothing to take back.
</ResponseField>

<ResponseField name="edit_window_expired" type="422">
  [Edit a message](/api-reference/messages/edit): more than 14 minutes 30 seconds have passed since `sent_at`. iMessage allows edits for 15 minutes; iBubbl stops 30 seconds early so an edit never arrives too late. Send a follow-up message instead.
</ResponseField>

<ResponseField name="edit_limit_reached" type="422">
  [Edit a message](/api-reference/messages/edit): the message has already been edited five times, the most iMessage allows.
</ResponseField>

<ResponseField name="link_changed" type="422">
  [Edit a message](/api-reference/messages/edit): the message was sent from the dashboard with a link preview, and the new text moves, changes or removes the link. Keep the link exactly as sent, at the end, and change only the text before it.
</ResponseField>

<ResponseField name="unsend_window_expired" type="422">
  [Unsend a message](/api-reference/messages/unsend): more than 110 seconds have passed since `sent_at`. iMessage allows 2 minutes; iBubbl stops 10 seconds early.
</ResponseField>

<ResponseField name="multi_part" type="422">
  [Unsend a message](/api-reference/messages/unsend): the message has files and text, or several files, so it shows as more than one bubble. Unsending part of a message is available in the dashboard only, for now.
</ResponseField>

<ResponseField name="not_cancellable" type="422">
  [Cancel a message](/api-reference/messages/cancel): the message isn't one of yours that is still waiting to go out. It was sent, failed or expired, it's a message you received, or it's a meeting invite. To take back one that went out, [unsend it](/api-reference/messages/unsend) within 110 seconds. On [Cancel a scheduled message](/api-reference/scheduled-messages/cancel): it has already fired or failed.
</ResponseField>

<ResponseField name="target_unsent" type="422">
  [Add a tapback](/api-reference/messages/react) and [Remove a tapback](/api-reference/messages/remove-reaction): the contact unsent the message, so it can't get (or lose) a tapback. Also a `failed_reason` on [`message.reaction.failed`](/webhooks/events) when they unsent it before the tapback went out.
</ResponseField>

<ResponseField name="target_partly_unsent" type="422">
  [Add a tapback](/api-reference/messages/react) and [Remove a tapback](/api-reference/messages/remove-reaction): the contact unsent part of the message, and your line can't place a tapback on what's left.
</ResponseField>

<ResponseField name="opt_out_check_unavailable" type="503">
  [Add a tapback](/api-reference/messages/react), [Edit a message](/api-reference/messages/edit) and [Start typing](/api-reference/conversations/start-typing): iBubbl couldn't confirm that the contact hasn't opted out, so it sent nothing. Retry after a short backoff. (Mark read doesn't fail this way: it answers `200` with `read_receipt_skipped_reason: "opt_out_check_unavailable"` and sends no receipt.)
</ResponseField>

<ResponseField name="no_active_line" type="503">
  [Schedule a message](/api-reference/scheduled-messages/create) to a contact you have no conversation with yet: your account has no active line to start one on. Nothing was scheduled and the `idempotency_key` stays unused, so send the same request again, with the same key, once a line of yours is active. A contact you named with `to` is created all the same. Not the same as `422 no_eligible_line`: that is a send no line can take right now, or a scheduled message that finds no line when it fires.

  [Look up a number](/api-reference/imessage-lookups/create): your account has no active line to ask Apple from. Nothing was queued.
</ResponseField>

<ResponseField name="limits_unavailable" type="503">
  [List lines](/api-reference/lines/list) and [Retrieve a line](/api-reference/lines/retrieve): the live limit counters of an active line couldn't be read. iBubbl answers with this instead of counts it couldn't confirm. Nothing is wrong with the line, and sends are unaffected. Retry after a few seconds.
</ResponseField>

<ResponseField name="first_message_needs_text" type="422">
  `POST /v1/messages` and [scheduled messages](/api-reference/scheduled-messages/create): you sent `attachments` without a `body` (or [removed the text](/api-reference/scheduled-messages/update) of a scheduled one) to a contact you've never exchanged a message with. Messages can't open a new conversation with files alone. Add a `body`. See [Captions and the first message](/guides/attachments#captions-and-the-first-message).
</ResponseField>

<ResponseField name="file_not_found" type="404">
  [Retrieve a file](/api-reference/files/retrieve), [Delete a file](/api-reference/files/delete), and `POST /v1/messages` when an `attachments` file ID names no upload of yours: it is malformed, belongs to another account, was deleted, or (on retrieve and delete) has expired. In a send, the `message` names it by position, for example `attachments[1]: no file file_3f2c… on this account`; nothing was created. Upload the file again and send its new `id`.
</ResponseField>

<ResponseField name="file_expired" type="422">
  `POST /v1/messages` only: an `attachments` file ID is past its `expires_at`, 24 hours after its upload. Nothing was created. Upload the file again and send its new `id`. See [Upload a file](/guides/attachments#upload-a-file).
</ResponseField>

<ResponseField name="file_quota_exceeded" type="422">
  [Upload a file](/api-reference/files/upload) only: your account already holds 500 files, or 1 GiB, of uploads that haven't expired. Nothing was stored. [Delete](/api-reference/files/delete) files you've sent, or wait for them to expire (24 hours after each upload).
</ResponseField>

<ResponseField name="upload_timeout" type="408">
  [Upload a file](/api-reference/files/upload) only: the body took over 5 minutes to arrive, or paused for over 30 seconds. Nothing was stored; upload again.
</ResponseField>

<ResponseField name="attachment_fetch_failed" type="422">
  `POST /v1/messages` only: iBubbl couldn't download one of the `attachments` URLs. The `message` names it by position, for example `attachments[1]: attachment fetch answered 404`. Causes: the host doesn't resolve or is a private or internal address, the server answered something other than `200`, more than 3 redirects (or one to a non-`https` URL), an empty file, or the download took too long (about 30 seconds for all the files, or 10 seconds without data). Check the URL works from the public internet, then send again. Nothing was created. See [Send attachments](/guides/attachments#how-the-urls-are-read).
</ResponseField>

<ResponseField name="attachment_too_large" type="422">
  `POST /v1/messages` and [Upload a file](/api-reference/files/upload): a file is over its kind's limit (images and GIFs 25 MiB, video 50 MiB, PDF 10 MB, audio 25 MiB), or the files are over 86 MB in all. The `message` names the file. Send a smaller file, or split the files across messages. See [Supported files and limits](/guides/attachments#supported-files-and-limits).
</ResponseField>

<ResponseField name="unsupported_attachment" type="422">
  `POST /v1/messages` and [Upload a file](/api-reference/files/upload): a file's type can't be sent through the API, for example a calendar invite (`.ics`), WebM or Ogg audio, SVG or a ZIP file. The type comes from the URL response's (or the upload part's) `Content-Type`, or the file name's extension when that is `application/octet-stream`. An upload is also refused when its content doesn't match its type (`the file's content isn't image/jpeg`). Convert the file to a supported type.
</ResponseField>

<ResponseField name="attachment_combination_not_supported" type="422">
  `POST /v1/messages` only: the files can't go out together with their caption. With other files, audio must be a single MP3 of 2 MB or less; any other audio, and a second audio file, needs a message of its own. Send it separately.
</ResponseField>

<ResponseField name="imessage_undeliverable" type="message.failed">
  Not an API error: it appears as `failed_reason` (and `error.code`) on a failed message, in [Retrieve a message](/api-reference/messages/retrieve) and its [`message.failed`](/webhooks/events) webhook. iMessage couldn't deliver the message to this number because the number isn't reachable on iMessage. Resending fails the same way, so reach the contact another way. Other iMessage failures appear as `imessage_error:<code>`.
</ResponseField>

<ResponseField name="internal_error" type="500">
  An unexpected error on iBubbl's side. These are paired with our error-tracking system; we get paged when they happen. If you see a sustained pattern, email [support@ibubbl.com](mailto:support@ibubbl.com) with the response's [`X-Request-Id`](#request-ids) header.

  One known cause: two `POST /v1/messages` requests with the same `idempotency_key` arriving at the same moment. Only one message is created, and the other request gets this `500`. Retrying it with the same key returns the `202` replay. See [Duplicates and retries](/concepts/message-lifecycle#duplicates-and-retries).
</ResponseField>

<ResponseField name="account_setup_incomplete" type="422">
  Your account has no active manager in the dashboard, so nothing can be sent: [Send a message](/api-reference/messages/send), [Schedule a message](/api-reference/scheduled-messages/create) and [Add a tapback](/api-reference/messages/react) all answer this. Add a manager, or reactivate one, in the dashboard, then send the same request again. Nothing was sent, so the `idempotency_key` is still unused. Before 2026-11-13 this was `500 no_owner_rep`.
</ResponseField>

<ResponseField name="invalid_url" type="422">
  A [`POST /v1/webhooks`](/api-reference/webhooks/create) `url` that doesn't start with `https://`. Webhook endpoints must use HTTPS.
</ResponseField>

<ResponseField name="invalid_signature" type="403">
  An [inbound event](/inbound-events/overview) arrived with a missing or incorrect signature. For Recharge, the usual cause is that the source was created with your API token pasted where the **API Client Secret** belongs — they're different values.
</ResponseField>

<ResponseField name="payload_too_large" type="413">
  An [inbound event](/inbound-events/overview) body exceeded 256 KiB (262,144 bytes).
</ResponseField>

<ResponseField name="feature_disabled" type="403">
  [Look up a number](/api-reference/imessage-lookups/create) and [Retrieve a lookup](/api-reference/imessage-lookups/retrieve): iMessage lookups have been turned off for your account (a `404` before 2026-11-13). They are on for every account unless support turns them off; email [support@ibubbl.com](mailto:support@ibubbl.com).
</ResponseField>

<ResponseField name="invalid_phone" type="422">
  [Look up a number](/api-reference/imessage-lookups/create): `phone` has the E.164 shape but isn't a valid number in its country. Nothing was looked up.
</ResponseField>

<ResponseField name="lookup_budget_exhausted" type="429">
  [Look up a number](/api-reference/imessage-lookups/create): every line that could ask Apple has used its lookup budget, 50 an hour and 100 a day (midnight to midnight, US Eastern) per line, shared with GoHighLevel **Check iMessage** steps. Nothing was queued. The `Retry-After` header is the seconds until one of those lines frees a slot; send the same request again then. Lookups iBubbl can answer from what it already knows never use the budget. See [Check iMessage availability](/guides/check-imessage-availability#limits).
</ResponseField>

<ResponseField name="lookup_unavailable" type="503">
  [Look up a number](/api-reference/imessage-lookups/create): the lookup couldn't be started. Nothing was queued; try again after a short backoff.
</ResponseField>

<ResponseField name="rate_limited" type="429">
  Returned in six places, and nowhere else:

  - **Conversation actions** ([Edit](/api-reference/messages/edit), [unsend](/api-reference/messages/unsend) and [cancel](/api-reference/messages/cancel) a message, [add](/api-reference/messages/react) and [remove](/api-reference/messages/remove-reaction) a tapback, [Mark read](/api-reference/conversations/mark-read), [start](/api-reference/conversations/start-typing) and [stop](/api-reference/conversations/stop-typing) typing, and [schedule](/api-reference/scheduled-messages/create), [update](/api-reference/scheduled-messages/update), [cancel](/api-reference/scheduled-messages/cancel) and [send now](/api-reference/scheduled-messages/send-now) a scheduled message): your account made more than 300 of these requests in 60 seconds (all API keys and all eleven endpoints together; a budget separate from lists). The response has a `Retry-After` header; wait that long and call again. See [Rate limits](/concepts/limits#rate-limits).
  - **List endpoints** ([List messages](/api-reference/messages/list), [List scheduled messages](/api-reference/scheduled-messages/list), [List contacts](/api-reference/contacts/list), [List lines](/api-reference/lines/list)): your account made more than 120 list requests in 60 seconds (all API keys and all lists together). The response has a `Retry-After` header with the seconds to wait; then send the same request again. See [Rate limits](/concepts/limits#rate-limits).
  - **[Uploads](/api-reference/files/upload)**: more than 60 uploads in 60 seconds from your account (all API keys together; a budget of its own), or 4 already in progress. The response has a `Retry-After` header; wait that long and upload again.
  - **[iMessage lookups](/api-reference/imessage-lookups/create)**: more than 60 lookup requests in 60 seconds from your account (all API keys together; a budget of its own). The response has a `Retry-After` header. Not the same as `lookup_budget_exhausted`, which is your lines' Apple lookup budget.
  - **Sends with attachment URLs**, rarely: iBubbl was already downloading as many attachment sends as it can, and no slot freed within 10 seconds. `Retry-After` is `5`; then send the same request with the same `idempotency_key`. Nothing was created.
  - **`/v1/events`**: a secret-URL [inbound event](/inbound-events/overview) source received more than 60 events in 60 seconds. There is no `Retry-After` header here; send again after about a minute.

  Text-only sends (`POST /v1/messages` without `attachments`) never return it.
</ResponseField>

## When to retry

| Code | HTTP | Retryable? |
| ---- | ---- | ---------- |
| `unauthorized` | 401 | ❌ Fix the key. |
| `forbidden` | 403 | ❌ Account suspended or cancelled; email [support@ibubbl.com](mailto:support@ibubbl.com). |
| `not_found` | 404 | ❌ Verify the ID. |
| `group_not_found` | 404 | ❌ Use the group's current `chat_guid`. |
| `line_not_found` | 404 | ❌ Use a `line_id` from List lines. |
| `idempotency_conflict` | 409 | ❌ Fix the retry logic. |
| `edit_in_flight` | 409 | ✅ After `message.edited` (a few seconds). |
| `already_unsent` | 409 | ❌ The message was unsent. |
| `message_dispatching` | 409 | ❌ It's being sent; unsend it within 110 seconds instead. |
| `scheduled_message_sending` | 409 | ❌ It's firing; read it again in a few seconds, then act on the message. |
| `scheduled_message_changed` | 409 | ⚠️ Read it again, then retry if the change still makes sense. |
| `validation_error` | 422 | ❌ Fix the payload or query parameters. |
| `invalid_cursor` | 422 | ❌ Use the last `id` from the previous page. |
| `contact_opted_out` | 422 | ❌ Cannot bypass. |
| `contact_blocked` | 422 | ❌ Not until the contact is [unblocked](/api-reference/contacts/unblock). |
| `unresponsive_contact` | 422 | ❌ Not until the contact replies. |
| `group_outbound_blocked_suppression` | 422 | ❌ Cannot bypass; leave out the opted-out participants. |
| `insufficient_participants` | 422 | ❌ Fix the participant list, or send one-to-one. |
| `reply_target_not_found` | 422 | ❌ Fix `reply_to_message_id`, or the addressing field. |
| `reply_target_unsent` / `reply_target_partly_unsent` | 422 | ❌ Send without `reply_to_message_id`. |
| `invalid_target` | 422 | ❌ Tapbacks go only on messages you received; edits and unsends only on messages you sent. |
| `sms_not_supported` | 422 | ❌ Not over SMS. |
| `not_sent_yet` | 422 | ❌ Cancel it instead. |
| `not_editable` / `not_unsendable` / `not_cancellable` | 422 | ❌ This message can't be changed that way. |
| `edit_window_expired` / `edit_limit_reached` / `unsend_window_expired` | 422 | ❌ Too late; send a follow-up message. |
| `link_changed` | 422 | ❌ Keep the link as sent, at the end. |
| `multi_part` | 422 | ❌ Use the dashboard. |
| `target_unsent` / `target_partly_unsent` | 422 | ❌ The contact unsent the message. |
| `first_message_needs_text` | 422 | ❌ Add a `body`. |
| `send_at_too_soon` / `send_at_too_far` | 422 | ❌ Pick a `send_at` 1 minute to 90 days ahead. |
| `scheduled_limit_reached` | 422 | ⚠️ After some scheduled messages fire, or after you cancel some. |
| `scheduled_group_unsupported` | 422 | ❌ Schedule one-to-one messages only. |
| `scheduled_empty` | 422 | ❌ Keep or send text, or cancel it. |
| `attachment_fetch_failed` | 422 | ⚠️ Fix or check the URL, then send again; the key is still unused. |
| `attachment_too_large` / `unsupported_attachment` / `attachment_combination_not_supported` | 422 | ❌ Change the files. |
| `file_not_found` | 404 | ❌ Upload the file again and send its new `id`. |
| `file_expired` | 422 | ❌ Upload the file again and send its new `id`. |
| `file_quota_exceeded` | 422 | ⚠️ Delete uploads you've sent, or wait for them to expire, then upload again. |
| `upload_timeout` | 408 | ✅ Upload again. |
| `invalid_url` | 422 | ❌ Use an `https://` URL. |
| `invalid_timezone` | 422 | ❌ Fix the timezone. |
| `invalid_email` / `invalid_tag` / `duplicate_tag` | 422 | ❌ Fix the value. |
| `line_offline` | — (`202`, `queued`) | ⚠️ Not an error: iBubbl queues and retries for up to an hour. Don't resend. |
| `daily_cap_exhausted` / `cold_cap_exhausted` | 422 | ⚠️ Not queued. Send again after the limit resets (midnight ET). |
| `hourly_cap_hit` / `followup_cap_exhausted` | — | Legacy: not used on any current line. |
| `no_eligible_line` | 422 | ⚠️ A send: send again once your line is back online. ❌ Edit, unsend, tapbacks, typing: the message's line is no longer on your account; don't retry. |
| `rate_limited` | 429 | ✅ Lists, conversation actions, uploads, lookups and attachment sends: send the same request again (same `idempotency_key`) after `Retry-After` seconds. `/v1/events`: after about a minute. |
| `lookup_budget_exhausted` | 429 | ✅ After `Retry-After` seconds, when one of your lines frees a lookup slot. |
| `feature_disabled` | 403 | ❌ Lookups are turned off for your account; email support. |
| `invalid_phone` | 422 | ❌ Fix the number. |
| `account_setup_incomplete` | 422 | ⚠️ Add or reactivate a manager in the dashboard, then send the same request again. |
| `lookup_unavailable` | 503 | ✅ Retry after a short backoff. |
| `invalid_signature` | 403 | ❌ Fix the signing secret. |
| `payload_too_large` | 413 | ❌ Fix the payload size. |
| `internal_error` | 500 | ✅ Retry with the same idempotency key after a short backoff. |
| `opt_out_check_unavailable` | 503 | ✅ Retry after a short backoff. |
| `limits_unavailable` | 503 | ✅ Retry after a few seconds. |
| `no_active_line` | 503 | ⚠️ Send the same request again (same `idempotency_key`) once a line of yours is active. Nothing was scheduled. |

The general rule: **don't retry 4xx**. Most 4xxes are payload-level problems that retrying won't fix. The exception is `429 rate_limited`: wait, then send the same request again (on a list, a conversation action, an upload or an attachment send, `Retry-After` says how long). The limit 422s (`daily_cap_exhausted`, `cold_cap_exhausted`) are retryable only after the limit resets at midnight ET; iBubbl does not queue them for you. The hourly new-contact limit and an offline line are different: those sends are accepted and wait (`pending` with `held_reason: "hourly_limit"`, or `queued`), so resending just creates a duplicate. The numbers are on [Limits and queues](/concepts/limits). A send refused with a `404` or `422` creates no message, so its `idempotency_key` stays unused and you can reuse it when you send again. The same holds for a scheduled message refused with `503 no_active_line`.

## HTTP status mapping summary

| Status | When |
| ------ | ---- |
| `200` / `201` / `202` / `204` | Success. `202` for accepted-but-queued sends, edits and unsends; `201` for created resources, including an [upload](/api-reference/files/upload) and a [scheduled message](/api-reference/scheduled-messages/create) (`200` for its retry); `204` (no body) for [Delete a contact](/api-reference/contacts/delete) and [Delete a file](/api-reference/files/delete); `200` everywhere else. |
| `401` | Auth failure. |
| `403` | Account suspended or cancelled (`forbidden`), iMessage lookups turned off for your account (`feature_disabled`), or an inbound event's signature failed (`invalid_signature`). |
| `404` | Resource not found (or hidden across tenants), `group_not_found`, `line_not_found` or `file_not_found`. |
| `409` | Idempotency conflict, or a message in a state another request holds: `edit_in_flight`, `already_unsent`, `message_dispatching`, `scheduled_message_sending`, `scheduled_message_changed`. |
| `408` | `upload_timeout`: an upload that took too long to arrive. |
| `413` | Inbound event body over 256 KiB. |
| `422` | Validation, routing or send-limit failure. |
| `429` | `rate_limited`: too many list requests, conversation actions, uploads or lookups from your account, or attachment downloads busy (all with `Retry-After`), or too many inbound events for one source on `/v1/events`. `lookup_budget_exhausted`: your lines' Apple lookup budget is used up (with `Retry-After`). |
| `500` | An unexpected iBubbl error (`internal_error`). |
| `503` | `opt_out_check_unavailable` on a tapback, edit or typing call, `limits_unavailable` on a lines read (retry after a short backoff), or `no_active_line` when scheduling to a contact you have no conversation with yet while no line of yours is active (send the same request again, same `idempotency_key`, once one is). On an [iMessage lookup](/api-reference/imessage-lookups/create): `line_offline`, `no_active_line` or `lookup_unavailable`, with nothing queued. |
| `502` / `503` without a `detail.error` | The network edge during a deployment blip, not iBubbl itself. Retry with the same idempotency key after a short backoff. |
