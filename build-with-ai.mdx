Coding agents write better iBubbl integrations when they read the docs instead of guessing. Everything on this site is available in forms an agent can read, and the system prompt below gives it the rules that are easy to get wrong.

## Docs for agents

| Resource | URL | Use it for |
| -------- | --- | ---------- |
| `llms.txt` | [`https://docs.ibubbl.com/llms.txt`](https://docs.ibubbl.com/llms.txt) | An index of every page, with a one-line summary and a link to its Markdown. |
| `llms-full.txt` | [`https://docs.ibubbl.com/llms-full.txt`](https://docs.ibubbl.com/llms-full.txt) | All of these docs in one plain-text file, to paste or attach as context. |
| Markdown pages | Add `.md` to any page URL, for example [`https://docs.ibubbl.com/api-reference/messages/send.md`](https://docs.ibubbl.com/api-reference/messages/send.md) | One page as clean Markdown. |
| OpenAPI spec | [`https://docs.ibubbl.com/openapi/public.json`](https://docs.ibubbl.com/openapi/public.json) | The machine-readable `/v1` contract: generate a client, or import it into Postman or Insomnia ([how](/openapi)). |
| Docs MCP server | `https://docs.ibubbl.com/mcp` | Lets an agent search and read these docs while it works. |

The menu at the top of each page can also copy the page as Markdown, open it in ChatGPT or Claude, or connect the MCP server to Cursor or VS Code.

### Connect the docs MCP server

The MCP server searches and reads these docs. It can't call the iBubbl API or send messages, and it doesn't need your API key.

<CodeGroup>

```bash Claude Code
claude mcp add --transport http ibubbl-docs https://docs.ibubbl.com/mcp
```

```json Cursor
{
  "mcpServers": {
    "ibubbl-docs": {
      "url": "https://docs.ibubbl.com/mcp"
    }
  }
}
```

</CodeGroup>

For Cursor, add the entry to `.cursor/mcp.json` in your project, or to `~/.cursor/mcp.json` for every project.

## System prompt for coding agents

Copy this into your agent's instructions (for example `CLAUDE.md`, `AGENTS.md` or `.cursor/rules`) before asking it to build an iBubbl integration. Each rule prevents a mistake that sends duplicate messages, messages people who opted out, or creates a reply loop.

```text
You are building an integration with the iBubbl API, which sends iMessages
(with a fallback to SMS) from a line that iBubbl runs for the customer.
Follow these rules exactly.

REFERENCE
- Base URL: https://api.ibubbl.com. Every endpoint is under /v1.
- Docs: https://docs.ibubbl.com. Full text: https://docs.ibubbl.com/llms-full.txt.
  OpenAPI: https://docs.ibubbl.com/openapi/public.json. Read them before using
  an endpoint or field; never guess names, fields or values.
- Auth: send "Authorization: Bearer <key>". Read the key from the
  IBUBBL_API_KEY environment variable. Never hard-code, log or print it, and
  never put it in browser or mobile code.
- Every request is live. There is no sandbox or test mode. While testing,
  send only to the developer's own phone number.

SENDING (POST /v1/messages)
- Exactly one of: to (E.164, e.g. +14155551234), contact_id, chat_guid,
  participant_phones. Plus idempotency_key (required) and body (required
  unless attachments are sent; see ATTACHMENTS).
- Generate ONE idempotency_key (a UUIDv4) per logical message, before the
  first attempt, and store it with the message. Reuse the same key and the
  identical payload on every retry. Never generate the key inside a retry
  loop. A new key with the same body sends a second, real message: iBubbl
  never deduplicates by content.
- After a timeout, resend with the same key and body: you get the original
  message back if it was accepted, so the contact gets exactly one. Exception:
  never auto-retry a timed-out participant_phones send (it can create a second
  group); wait for its message.sent webhook first.
- 202 means accepted, not delivered. Track the outcome with webhooks or
  GET /v1/messages/{id}. A message outside the contact's sending hours stays
  "pending" with held_reason and held_until set; that is normal, not an error.
- The request has no field for the sending line. Unknown fields such as from
  or line_id are ignored without an error; each contact sticks to one line.
  Every message (send response, GET, list) says which line it was on:
  line_id and line_number (the line's E.164 number). "to" is always the
  contact's number, in both directions. Every message.* webhook carries
  line_id too (message.reaction.* events don't).
- Read the message's channel before assuming iMessage-only behaviour:
  "imessage" or "sms" (RCS also reports as "sms"); null until it is sent.
  The message.* webhooks carry the same channel field (from message.sent on,
  and on message.inbound for received messages); message.queued does not.
- Optional reply_to_message_id (an inline quote) and effect (one of 13
  iMessage effects, e.g. "confetti") are iMessage only: on SMS the message
  goes out as plain text without them. reply_to_message_id must be a message
  in the same conversation (the same contact, or the same group), else 422
  reply_target_not_found. Neither is allowed with participant_phones.

ATTACHMENTS (POST /v1/messages; https://docs.ibubbl.com/guides/attachments)
- attachments: 1-10 items, in order, each an https URL or an uploaded file
  id (file_ + 32 lowercase hex), mixed freely; 1:1 only (to or contact_id;
  never with chat_guid or participant_phones). iBubbl downloads URLs during
  the request: set the client timeout to 60 s for sends with URLs.
- body is optional with attachments (it is the caption), but the first
  message to a contact must have a body, else 422 first_message_needs_text.
- Types and limits: JPEG/PNG/WebP/HEIC/HEIF and GIF 25 MiB each, MP4/MOV
  50 MiB, PDF 10 MB, MP3/M4A/AAC audio 25 MiB alone; 86 MB in all. With other
  files, audio must be one MP3 of at most 2 MB, else 422
  attachment_combination_not_supported. No .ics, WebM, Ogg, SVG, ZIP.
- Errors (422, nothing created, key reusable): attachment_fetch_failed (URL
  not reachable/public, non-200, too slow), attachment_too_large,
  unsupported_attachment, attachment_combination_not_supported,
  file_expired; 404 file_not_found for a file id that is not this account's
  or was deleted. The message names the file as attachments[i].
- The items, in order, are part of the idempotency payload; a replay never
  downloads or copies again. effect and reply_to_message_id are not allowed
  with attachments (422 validation_error): send them as a separate message.
- Response: every message has attachments: [{kind, mime_type, size_bytes,
  filename}] ([] for text). filename is the name the recipient sees (null
  for received files). No file contents or URLs.

FILES (POST /v1/files, GET and DELETE /v1/files/{id};
https://docs.ibubbl.com/api-reference/files/upload)
- Use when a file has no public https URL. multipart/form-data with exactly
  one part named "file"; never set the request's Content-Type yourself. Set
  the part's type (e.g. application/pdf); with application/octet-stream the
  file name's extension decides. The content must match the type, else 422
  unsupported_attachment. Same types and caps as attachments.
- The part's file name is what the recipient sees (cleaned; the extension
  is always the type's own). Name files the way they should arrive.
- 201 returns {id, filename, kind, mime_type, size_bytes, created_at,
  expires_at}. Put id in attachments. One upload can be sent any number of
  times, to any contacts, until expires_at (24 h after upload); do not
  re-upload per send. After expiry: 422 file_expired; upload again.
- Uploads have no idempotency key: a retried upload stores a second file
  (the spare expires). 60 uploads a minute and 4 at once per account (429
  rate_limited, Retry-After). At most 500 live files / 1 GiB per account
  (422 file_quota_exceeded): DELETE files you have finished with. 408
  upload_timeout if the body takes over 5 minutes. Use a 120 s client
  timeout for uploads.

LIMITS (per line; https://docs.ibubbl.com/concepts/limits)
- 50 new contacts a day (resets at midnight America/New_York); the 51st gets
  422 cold_cap_exhausted.
- 30 new contacts per rolling 60 minutes; extra ones stay "pending" with
  held_reason "hourly_limit" and go out by themselves. Do not resend them.
- 1,000 outbound messages a day, every kind counted; then 422
  daily_cap_exhausted.
- 6 unanswered messages in a row to a contact who never replied; the 7th gets
  422 unresponsive_contact.
- No HTTP rate limit on POST /v1/messages (a text send never gets a 429; a
  send with attachment URLs rarely gets 429 rate_limited, Retry-After 5), but a
  line sends one message at a time (about one a second). Send one request at
  a time per line; bursts only build a queue. Pace outreach to new contacts
  at about one every 2 minutes per line.
- A "queued" message (line offline) that expires after about an hour fires
  message.failed with status "expired" and failed_reason "queue_expired".
  Branch on failed_reason, not status. Its idempotency_key is released.

LINES (GET /v1/lines, GET /v1/lines/{id})
- Lists the account's lines (same pagination and rate limit as READING
  HISTORY; filter status=active|paused|retired). Each line: id,
  phone_number, status, online (active lines: checked in within 2 minutes;
  false means sends wait as "queued"; null otherwise), created_at, limits.
- limits (null unless status is "active"): new_contacts_today {used, limit,
  resets_at}, new_contacts_this_hour {used, limit, waiting, next_slot_at},
  messages_today {used, limit, resets_at}. limit is the line's limit today
  and can be lower than 50/30/1,000; room left = max(0, limit - used).
- Read it once before a batch of first messages to new contacts, not
  before every send. Counts can change between the read and the send, so
  still handle cold_cap_exhausted and daily_cap_exhausted.
- 404 line_not_found for an id that isn't one of the account's lines;
  503 limits_unavailable means the counters couldn't be read: retry
  shortly, never treat it as zero.

READING HISTORY (GET /v1/messages)
- Lists inbound and outbound messages, newest first, as
  {"data": [...], "has_more": bool}. limit is 1-100 (default 50).
- Next page: repeat the same request with starting_after = the id of the LAST
  item in data. Stop when has_more is false. Never use page numbers or
  offsets, and never change the filters between pages.
- Filters: contact_id, conversation_id, chat_guid, direction
  (inbound/outbound), status, created_after, created_before (ISO 8601 with
  Z, e.g. 2026-11-10T09:30:00Z; both exclusive).
- An unknown or repeated query parameter is 422 validation_error, and a
  starting_after that isn't one of your ids is 422 invalid_cursor. Use the
  exact parameter names above.
- Rate limit: 120 list requests per 60 seconds per account, shared by all
  API keys and all list endpoints. Over it: 429 rate_limited with a
  Retry-After header (seconds). Sleep that long, then send the SAME request
  again (same starting_after); the refused request didn't count. Fetch
  pages one at a time; don't run parallel loops to go faster.
- To catch up after missed webhooks: list with created_after = your last
  processed created_at minus 5 minutes, skip message ids you already have,
  and store each message's status as returned (it is current).
  https://docs.ibubbl.com/guides/webhook-retries#recover-from-downtime

CONTACTS (/v1/contacts)
- POST /v1/contacts upserts by E.164 phone (201 new, 200 existing) and only
  fills empty fields; PATCH /v1/contacts/{id} overwrites. Unknown body fields
  are 422 validation_error.
- GET /v1/contacts lists contacts newest first, with the same pagination and
  rate limit as READING HISTORY. Filters: search (every word must match a
  name, email or phone; phone digits match too), tag (ignores case),
  opted_out, blocked (true/false). Use the exact parameter names.
- DELETE /v1/contacts/{id} answers 204 with no body; afterwards the id is
  404 everywhere, including as a send's contact_id. History stays. The same
  number later becomes a NEW contact with a new id. Deleting never clears an
  opt-out.
- POST /v1/contacts/{id}/opt-out is PERMANENT: nothing can undo it. Call it
  only when the person asked not to be messaged, never to clean up a list or
  in tests with a real person's number. A repeat call is 200 with no second
  contact.opted_out event.
- To pause messages, block instead: POST /v1/contacts/{id}/block (sends get
  422 contact_blocked) and DELETE /v1/contacts/{id}/block to undo. A block
  fires no webhook and doesn't affect group conversations.
- Neither opt-out nor delete cancels a message already accepted and still
  waiting; cancel it with POST /v1/messages/{id}/cancel (see below).

TAPBACKS, READ RECEIPTS AND TYPING
- message.inbound carries message_id and conversation_id; use them directly.
- POST /v1/messages/{message_id}/reactions {"type": "love"|"like"|"dislike"|
  "laugh"|"emphasize"|"question"}: only on a RECEIVED message (else 422
  invalid_target). 201 pending; the same type again is 200 and sends
  nothing; a different type replaces it. Delivery fires
  message.reaction.added (direction "outbound"); a failure fires
  message.reaction.failed. Not over SMS (422 sms_not_supported).
  DELETE /v1/messages/{message_id}/reactions/{reaction_id} removes it.
- POST /v1/conversations/{conversation_id}/read marks the whole conversation
  read and sends a read receipt; read_receipt is "queued" or "skipped" (with
  a reason). Never in groups or to blocked/opted-out contacts. It also
  clears the dashboard's unread badge.
- POST /v1/conversations/{conversation_id}/typing shows the typing dots for
  10 seconds: call it on message.inbound and again every 5 seconds while
  generating a reply; sending the reply clears them. status "ignored"
  (group, not_imessage, no_chat) is normal, not an error. DELETE the same
  path only if you decide not to reply.
- Tapback and typing calls to a blocked or opted-out 1:1 contact get 422
  contact_blocked / contact_opted_out; 503 opt_out_check_unavailable means
  retry later.
- These endpoints, edit/unsend/cancel below, and the scheduled-message
  writes share 300 requests per 60 seconds per account (429 rate_limited with Retry-After), separate from the
  list budget.

EDIT, UNSEND AND CANCEL (messages you sent)
- POST /v1/messages/{id}/edit {"body": "..."} changes the text: iMessage
  only, within 14 min 30 s of sent_at, at most 5 edits. 202 with
  edit_status "pending"; message.edited (direction "outbound") fires when it
  lands, message.edit_failed if not (body goes back). The text it already has
  is 200 and spends nothing. One edit at a time: 409 edit_in_flight means
  wait for message.edited. A dashboard message with a link preview keeps its
  link last and unchanged (422 link_changed).
- POST /v1/messages/{id}/unsend takes a message back: iMessage only, within
  110 s of sent_at. 202 with unsend_status "pending", body ""; then
  message.unsent (scope "message") or message.unsend_failed. Repeat calls are
  200. A message with files and text, or several files, is 422 multi_part.
- NEVER rely on unsend for compliance or to retract sensitive data: older
  iPhones/Macs keep the original, and SMS/RCS messages can't be unsent or
  edited at all (422 sms_not_supported).
- POST /v1/messages/{id}/cancel stops a message still pending or queued
  (e.g. held for sending hours): 200 status "cancelled", message.cancelled
  fires, repeat calls are 200. 409 message_dispatching = too late, it goes
  out; 422 not_cancellable = already sent (unsend it instead). Edit/unsend
  of a message not sent yet is 422 not_sent_yet: cancel it instead.
- A message with a link preview card is two bubbles (text, then card): edit
  changes only the text before the link; unsend takes back both.

LINK PREVIEW CARDS
- A link in POST /v1/messages arrives as plain text unless you set
  "link_preview": true. The body must END in exactly one http(s) link with no
  other link before it; one-to-one only; not with attachments, effect or
  reply_to_message_id (all 422 validation_error).
- The line fetches the page at send time to build the card: that counts as
  a click. NEVER set link_preview on one-time links (login, password reset,
  single-use invites or coupons) or on links whose clicks you track.
- link_preview is part of the idempotency payload when true; the response
  echoes it.

SCHEDULED MESSAGES (POST/GET /v1/scheduled-messages, GET/PATCH
/v1/scheduled-messages/{id}, POST /v1/scheduled-messages/{id}/cancel,
POST /v1/scheduled-messages/{id}/send-now;
https://docs.ibubbl.com/guides/schedule-messages)
- Use instead of your own cron to send a 1:1 message later. Body = a 1:1
  send (to OR contact_id, body, attachments, effect, reply_to_message_id,
  link_preview)
  plus send_at: ISO 8601 WITH a time zone (Z or an offset), 1 minute to 90
  days ahead (422 send_at_too_soon / send_at_too_far; no zone = 422
  validation_error). Groups: 422 scheduled_group_unsupported. Any unknown
  field: 422 validation_error. link_preview has the same rules as on a
  send (422 validation_error otherwise) and is re-checked on every PATCH.
- 201 returns a scheduled message {id, status, send_at, to, contact_id,
  conversation_id, body, attachments, effect, reply_to_message_id,
  link_preview, message_id, fired_at, failed_reason, created_at,
  updated_at}. Its id is NOT a message id. status: scheduled -> sending
  -> fired | failed, or cancelled. On fired, message_id is the new
  message: follow THAT for delivery (it may still wait for sending hours
  or limits).
- idempotency_key is required and SHARED with POST /v1/messages: a key used
  on one is 409 idempotency_conflict on the other. Same key + same payload =
  200 with the current state; a different send_at is a 409 (use PATCH).
  Never use keys starting with "sched:" (422).
- 503 no_active_line: no conversation with the contact yet AND no active
  line to start one on. Nothing scheduled, key unused: send the same
  request (same key) once a line is active. A `to` contact is still
  created. Not 422 no_eligible_line (a send no line can take now, or a
  scheduled message that finds no line when it fires).
- send_at is when the message is created; iBubbl doesn't shift it to the
  contact's time zone. Outside the contact's sending hours, it fires at
  send_at but goes out when the window opens.
- Opt-out, block and the contact are checked again when it fires: refused =
  status failed, failed_reason set, webhook scheduled_message.failed, NO
  message and no message.* event. Also failed: missed_window (> 6 h late).
- PATCH {body?, send_at?, link_preview?} only while status is "scheduled". "body": null
  removes the text (only with files; 422 scheduled_empty otherwise). 409
  scheduled_message_sending = it is firing now; 422 not_editable /
  not_cancellable = already fired/failed. Cancel is repeat-safe (200).
  409 scheduled_message_changed = another request changed it at the same
  moment: read it again, then retry.
- POST .../{id}/send-now fires it IN the request: 200 with status "fired"
  + message_id (or "failed" + failed_reason). No 1-minute minimum.
  Repeat-safe: sending/fired answer 200 and nothing is sent twice;
  failed/cancelled = 422 not_editable. The message still waits for
  sending hours and limits once created.
- Webhooks: scheduled_message.fired | failed | cancelled, data = the
  scheduled message. message.* for the new message can arrive BEFORE
  scheduled_message.fired: match by message_id.
- Files are downloaded/copied when scheduled (uploads may expire after).
  5,000 waiting per account (422 scheduled_limit_reached). Create, update,
  cancel and send-now use the 300/min action budget; the list uses the list budget.

IMESSAGE LOOKUPS (POST /v1/imessage-lookups, GET /v1/imessage-lookups/{id};
https://docs.ibubbl.com/guides/check-imessage-availability)
- Never look a number up before a plain text: iBubbl already picks iMessage
  or SMS on every send. Look up only before iMessage-only content (an effect,
  a flow that edits or unsends later, an iMessage-only branch).
- POST {"phone": E.164}. 200 = answered now (status "completed"); 202 =
  pending, the answer arrives by the imessage_lookup.completed webhook or
  GET. A repeat while pending returns the same lookup.
- result: imessage | not_imessage | unknown. unknown is NOT a no (reason:
  timeout | lookup_failed | line_unavailable): send something that works
  either way, or look up again later. A completed lookup never changes.
- Budget: 50 Apple lookups an hour and 100 a day per line (shared with
  GoHighLevel checks); over it, 429 lookup_budget_exhausted with Retry-After,
  nothing queued. 60 requests a minute per account (429 rate_limited). Never
  bulk-look-up a whole list; look up only numbers you are about to message.
- 404 feature_disabled = lookups are turned off for the account; don't
  retry.

RETRIES AND ERRORS
- Branch on detail.error (the stable code), never on detail.message.
- Log the X-Request-Id response header with every error; quote it to
  support@ibubbl.com.
- Network error, timeout or 5xx: retry with the SAME idempotency_key and
  the same payload, with exponential backoff (1 s, 2 s, 4 s) and a small cap
  on attempts. Exception: 500 no_owner_rep will not succeed on retry.
- Never retry a 4xx automatically. Fix the request instead. The one
  exception: 429 rate_limited (a list, a tapback/read/typing call, a
  scheduled-message write, an upload, or an attachment send); wait Retry-After seconds, then repeat the same
  request (same idempotency_key).
- 422 unresponsive_contact: the contact has not replied to 6 messages in a
  row. Stop messaging them until they reply.
- 422 contact_opted_out: final. Never message this contact again, and never
  work around it (another number format, a group, deleting and re-creating
  the contact, another key or account).
- 422 contact_blocked: your account blocked this contact. Don't retry; only
  unblock if the user asks for it.
- 422 daily_cap_exhausted or cold_cap_exhausted: not queued. Do not send
  again before midnight ET.

WEBHOOKS
- Subscribe with POST /v1/webhooks {url, event_types}; any other field is
  422 validation_error (so a typo can't subscribe you to everything).
- Verify the X-iBubbl-Signature header on every request before trusting the
  body: HMAC-SHA256 of "{t}.{raw body bytes}" keyed with the whsec_ secret,
  compared in constant time; reject if t is more than 300 seconds old. Read
  the header name case-insensitively. Details:
  https://docs.ibubbl.com/guides/webhook-signatures
- Return a 2xx within 10 seconds and do the work asynchronously.
- Delivery is at least once and in no guaranteed order. Deduplicate on the
  event id (evt_...) before doing anything.
- Only message.inbound may trigger an automated send. Never send in response
  to message.queued, message.sent, message.delivered, message.read,
  message.failed, message.cancelled, message.edited or a reaction event, or
  to any event about your own outbound messages: that creates a loop.
- contact.opted_out: mark the contact do-not-contact in your own system.
- Return a 2xx for event types and enum values you don't recognise; iBubbl
  adds new ones over time.
```
